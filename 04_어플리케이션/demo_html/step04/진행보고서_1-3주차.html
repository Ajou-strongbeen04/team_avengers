0. 과제 개요

관상어 사육자가 어항의 이상을 알아채기 전에 알려주는 시스템이다. 수온과 탁도만 센서로 재고, 물고기의 생존을 실제로 좌우하는 용존산소는 물리 모델로 추정한다. 용존산소 센서는 가정용으로 쓰기에 너무 비싸고 교정 주기가 짧다는 점이 이 접근의 출발점이다.

계층담당
프로브 (하드웨어) DS18B20 방수 수온센서(1-Wire), IR LED 850nm + 포토트랜지스터(광학경로 50mm). 투과광 감쇠량으로 탁도를 측정한다.
ESP32-WROOM-32 R-DAC 8단 전류구동 → ADC 측정 → 암전류 보정·오토레인징·NTU 환산 → BLE GATT Notify (1초 주기, "수온,탁도" CSV)
안드로이드 앱
(Capacitor WebView)		 실시간 모니터링, 상태 판정, 알림 엔진, 측정 기록, 어항·어종 프로필, 용존산소 물리 모델 실행
Gemini API 어항 사진 → 구조물 3D 좌표·크기 추정(ROM 입력), 측정값 맥락 기반 AI 사육 상담

설계 요점 — ESP32 한 개가 광원 구동·수광 측정·신호 처리를 모두 담당한다. 연산 증폭기나 커패시터 없이 저항 사다리(R-DAC)와 ADC 조합만으로 아날로그 프런트엔드를 대체해 부품 수와 실패 지점을 줄였다. 앱은 웹 코드 한 벌을 Capacitor로 감싸고 BLE만 네이티브로 붙였다.

본 보고서의 시행착오 기재 방식
기록한 시행착오는 모두 소스 주석과 커밋 산출물에 근거가 남아 있는 것만 실었다. 각 항목의 근거 위치를 파일·줄번호로 표기했다. 추정으로 채운 내용은 없으며, 근거가 확인되지 않은 항목은 「미확인」으로 표시했다.

1주차 — 센서 프로브·펌웨어 제작 및 BLE 연동

목표 — ESP32로 수온·탁도를 안정적으로 측정하고, 그 값을 BLE로 안드로이드에 1초 주기로 올린다. 용존산소 센서 없이 탁도를 정량화하는 광학 측정 경로를 확보하는 것이 핵심이다.

1.1 수행 내용

  • 탁도 측정 원리 구현 — 받은 빛의 절대량은 LED 노화·온도에 흔들린다. 그래서 비율값을 쓴다: ratio = (SIG점등 − SIG소등) / I_LED. 분자의 뺄셈이 주변광을 지우고 분모의 나눗셈이 LED 밝기 변화를 지운다. 최종 환산은 램버트–비어 법칙 NTU = K × (−log₁₀(ratio / ratio_clear)).
  • R-DAC 8단 전류 구동 — GPIO 3개(25·26·27)에 150/330/680Ω을 물려 8단계 LED 전류를 만들고, 물이 맑을 때는 약하게, 탁할 때는 강하게 쏘는 오토레인징을 구현했다.
  • BLE GATT 서버 — 1초 주기 Notify, 페이로드는 20바이트 이내 CSV. 무효값은 수온 −99, 탁도 −1 센티널로 구분해 보낸다.
  • 탁도 영점 보정 — 깨끗한 물에 담근 상태에서 CAL_CLEAR 명령으로 현재 ratio를 0 NTU 기준으로 저장한다.
  • 안드로이드 BLE 연동 — @capacitor-community/bluetooth-le로 스캔·연결·Notify 구독. 기기 목록 UI를 자체 구현했다.

1.2 문제점과 해결 — 펌웨어

증상원인해결
컴파일 에러
'TurbidityRaw' does not name a type		 아두이노 IDE는 컴파일 전 .ino를 훑어 함수 프로토타입을 자동 생성해 파일 첫 줄에 끼워 넣는다. .ino 안에 struct를 두면 프로토타입이 struct 정의보다 위에 놓인다. struct를 파일 맨 위로 올려도 삽입 지점이 더 위여서 해결되지 않았다. 사용자 정의 타입을 aqua_sense_types.h로 분리했다. #include는 전처리기 지시문이라 프로토타입 삽입 지점이 그 뒤로 밀린다. aqua_sense_types.h:4-16
R-DAC OFF 시 나머지 비트의 전류 가중치가 전부 틀어짐 OFF를 digitalWrite(LOW)로 처리하면 그 저항이 노드를 GND로 끌어내리는 병렬 경로가 되어 버린다. OFF는 반드시 pinMode(INPUT) 하이임피던스로 처리. ON 전환 시에도 HIGH를 먼저 걸고 OUTPUT으로 바꾼다 (순서를 반대로 하면 출력 레지스터 초기값 0 때문에 수 µs 글리치가 생긴다). aqua_sense_esp32.ino:128-146
「레벨 숫자가 클수록 전류가 크다」는 가정이 실배선에서 깨져 오토레인징이 엉뚱한 순서로 탐색 어느 GPIO에 어느 저항이 물렸는지에 따라 전류 크기 순서가 뒤바뀔 수 있다. 부팅 시 7단계 전류를 실제로 측정해 내림차순 탐색 순서(scanOrder)를 만든다. 단일 비트 전류로 저항값을 역산해 배선 확인용 진단 로그도 출력한다. aqua_sense_esp32.ino:216-279
전류 측정(SENSE) 핀의 실효 분해능이 유효범위의 8%밖에 안 됨 SENSE는 22Ω 션트라 전체 스윙이 56~355 mV인데, 11 dB 감쇠(정확구간 150~2450 mV)로 읽고 있었다. SENSE만 0 dB(정확구간 약 100~950 mV)로 낮춰 분해능을 약 3배 개선했다. 션트를 100Ω으로 바꾸면 전 구간이 정확구간에 들어온다는 개선안을 주석에 남겼다(미실행). aqua_sense_esp32.ino:378-383
멀쩡한 물이 「매우 탁함」으로 표시됨 포화 판정을 차분값으로 했다. 조명이 켜져 암전류 기준이 이미 높으면 점등값이 완전히 포화해도 차분은 정상 범위처럼 보인다. 최악의 경우 둘 다 포화되어 차분≈0 → 항상 최대 NTU가 나온다. 포화 판정은 반드시 원시값으로 한다. aqua_sense_esp32.ino:194-198
수조 조명이 프로브를 직사하면 구동 레벨을 낮춰도 측정 불가 주변광만으로 이미 포화된 상태에서는 오토레인징을 7회 반복해도 해결되지 않는다. ambientBlind 플래그로 따로 표시하고 오토레인징 루프를 즉시 중단해 헛측정을 막는다. 차광이 필요하다고 경고한다. aqua_sense_esp32.ino:200-205, 291-295
첫 수온 읽기값이 85.00°C DS18B20은 12비트 변환에 750 ms가 걸린다. 파워온 직후 읽으면 레지스터 기본값(85.00)이 나온다. 첫 측정을 한 주기 뒤로 미뤘다. 오류 필터 상한도 90이 아니라 84로 잘라 85가 정상값으로 통과하지 못하게 했다(어항이 84°C를 넘을 일은 없다는 전제). aqua_sense_esp32.ino:434-436, 463-467
센서를 뽑아도 앱에는 마지막 정상 온도가 계속 전송되어 화면이 「정상」으로 얼어붙음 연속 실패를 누적하지 않으면 낡은 값이 계속 흘러간다. 값이 멈춘 채 양호로 표시되는 것이 가장 위험한 실패 방식이다. 5회 연속 실패 시 마지막 값을 NaN으로 폐기하고, BLE에는 −99를 보낸다. 0을 보내면 앱이 「0.0°C 위험」으로 표시해 저온인지 고장인지 구분되지 않는다. aqua_sense_esp32.ino:471-475, 534-537
영점 보정을 포화·오류 상태에서 누르면 몇 분 전 값이 기준으로 저장됨 마지막 ratio만 보면 그 값이 언제 측정된 것인지 알 수 없다. lastRatioFresh 플래그로 「직전 주기가 실제 유효 측정이었는가」를 표시하고, false면 보정을 거부한다. aqua_sense_esp32.ino:115-117, 348-355, 444-452
화면에 -0.0 NTU가 찍힘 -log10f(1.0)이 -0.0을 반환하고, IEEE 754 규칙상 (-0.0 < 0.0)이 거짓이라 하한 클램프를 그냥 통과한다. if (!(ntu > 0.0f)) ntu = 0.0f;로 부호를 명시적으로 털어냈다. aqua_sense_esp32.ino:320-323

1.3 문제점과 해결 — BLE 연동

증상원인해결
BLE 스캔이 에러 없이 빈 목록을 반환 매니페스트에 BLE 권한이 없었다. 예외도 안 나고 결과만 비어서 원인을 찾기가 매우 어려웠다. 안드로이드 12에서 권한 체계가 바뀌어 BLUETOOTH_SCAN/CONNECT가 필요한데, 11 이하 호환까지 함께 선언해야 한다. 권한을 손으로 넣으면 npx cap add android가 매니페스트를 재생성할 때마다 날아간다. 그래서 scripts/patch-manifest.js를 만들어 sync마다 자동 주입·검사하게 했다. scripts/patch-manifest.js:1-11, 26-49
Missing permissions: ACCESS_FINE_LOCATION 매니페스트에 maxSdkVersion="30"으로 조건부 선언해도, BLE 플러그인이 그 조건을 읽지 못하고 「권한 없음」으로 판단한다. Ble.initialize({ androidNeverForLocation: true })를 명시했다. app_demo.html:1450-1457
재연동을 반복하면 Notify 콜백이 중복 호출되거나 아예 오지 않음 ① 리스너가 누적됨. ② 이벤트 키의 UUID는 소문자여야 하는데 deviceId(대문자 MAC)까지 통째로 소문자화해 키가 어긋났다. 매번 removeAllListeners() 후 재등록하고, UUID만 소문자화한다. 플러그인 버전차에 대비해 deviceId는 원본·소문자 둘 다 등록한다. app_demo.html:1458-1485
플러그인 기본 기기 선택창이 항목을 눌러도 반응 없음 플러그인 제공 다이얼로그의 동작 문제. requestLEScan으로 직접 스캔하고 목록도 앱이 렌더링한다. 8초 뒤 자동 중지하되(배터리·강제종료 방지) 목록은 남겨 고를 수 있게 했다. app_demo.html:1568-1571, 1622-1641
연결이 끊긴 뒤 재연결 불가 광고를 재시작하지 않으면 재연결 자체가 불가능하다. 연결 해제 콜백에서 500 ms 대기(스택 정리) 후 광고를 다시 시작한다. aqua_sense_esp32.ino:543-548
탁도 프로브 미완성에 대한 대응 — 프로브 제작이 늦어져 TURBIDITY_MODE를 3단(0=정상 / 1=미장착→무효값 / 2=시연용 가상값)으로 분리했다. 모드 2는 실측이 아니므로 「발표에서 밝히지 않으면 결과 조작」이라고 시리얼 출력과 주석에 명시해 두었다. 가상값도 순수 랜덤워크가 아니라 8 NTU로 회귀하는 항을 넣어 물리적으로 그럴듯하게 움직이도록 했다. aqua_sense_esp32.ino:56-72, 486-497

1.4 다음 주 계획

안드로이드 앱의 화면 흐름과 알림 엔진을 구현한다. 센서값을 받아 보여주는 것에서 「이상을 판단해서 알려주는 것」으로 넘어가는 단계다.

2주차 — 안드로이드 앱·알림 엔진·측정 기록

목표 — 센서값을 어종별 기준과 대조해 상태를 판정하고, 상태가 바뀔 때만 알린다. 측정 이력을 폰에 저장해 추이를 볼 수 있게 한다. 오프라인 발표 환경에서도 동작하는 빌드 파이프라인을 만든다.

2.1 수행 내용

  • 화면 흐름 — 스플래시 → 온보딩(어항 사진·실측) → 센서 페어링 → 물고기 프로필 → 메인(홈·모니터링·기록·AI 상담).
  • 편차 게이지 통일 — 수온은 적정범위 중앙값 대비 편차(양방향 악화), 탁도는 0 NTU 기준 편차(단방향 악화)로 물리량이 다르지만, 동일한 편차 기반 게이지 컴포넌트로 렌더링해 사용자가 두 번 학습하지 않게 했다. 차트 라이브러리 없이 SVG로 직접 그려 CDN 의존을 하나 줄였다.
  • 알림 엔진 — 상태 전이 시점에만 알림을 남긴다. 진동 억제 2중 장치를 넣었다.
  • 측정 기록 — 구간 평균으로 축약 저장하고 SVG 꺾은선 그래프로 표시. 최근 7일 보관.
  • 빌드 파이프라인 — build.js(단일 원본 복사), patch-manifest.js(권한 주입), fetch-tailwind.js(오프라인 스타일 확보).

2.2 문제점과 해결 — 알림 엔진

증상원인해결
경계값 근처에서 「올라갔어요 / 내려갔어요」가 몇 초 간격으로 번갈아 쌓여 알림 목록이 못 쓰게 됨 매 갱신마다 판정하면 4초에 하나씩 같은 알림이 수백 개 쌓인다. 2중 억제 — ① 같은 상태가 연속 3회 관측돼야 확정 ② 같은 항목은 60초 이내 재알림 금지. app_demo.html:3101-3102, 3355-3379
「주의」 10초 뒤 「경고」로 악화됐는데 위험을 끝까지 통보하지 못함 최소 간격에 걸렸을 때 상태값을 먼저 갱신해 버렸다. 그러면 억제된 전이가 다음 관측에서 「이미 그 상태」로 걸러져 다시 알릴 기회가 영영 사라진다. 최소 간격에 걸리면 상태를 확정하지 않고 그냥 반환한다. 다음 관측에서 다시 판정 기회를 얻는다. app_demo.html:3366-3370

2.5 다음 주 계획

기계팀에서 검증한 용존산소 물리 모델을 앱에 통합한다. 지금까지 화면에 표시하던 용존산소는 자리표시자용 선형 근사식(9.0 − 0.15ΔT − 0.05·NTU)이었고, 이를 CFD로 검증된 물리 수지식으로 교체하는 것이 다음 단계의 핵심이다.

3주차 — 용존산소 물리 모델 통합 및 기능 확장

목표 — CFD 315케이스로 검증한 용존산소 물리 모델을 앱에 통합한다. 사용자가 실제로 쓸 수 있는 입력(기포기 정격전력, 여러 어종)으로 받고, 앱을 보고 있지 않을 때도 위험을 알리며, 앱을 껐다 켜도 설정이 남게 한다.

3.1 수행 내용

(1) 물리 모델 통합

완전혼합 정상상태 수지식으로 용존산소를 추정한다.

C = C*(T) − R_total / (V · K_La),   R_total = 어류 + 유기물(탁도) + 식물(주야)

0-D 축약의 근거 — 47×21×21 cm 폭기 ON 조건에서 폭기 플룸 이류 순환은 12.8초, 난류확산은 3,060초, 산소 소비는 9.5시간이다. 이류가 소비보다 2,673배 빠르다. 즉 어디서 산소를 쓰든 물이 그보다 훨씬 빨리 순환해 채우므로, 공간을 풀지 않고 0차원 수지로 축약할 수 있다. 실측 축약 오차는 용존산소 기준 0.11%(0.0091 mg/L)였다.

등급은 평균이 아니라 최저 지점 기준으로 판정한다. 평균이 안전해도 바닥 구석이 임계 미만이면 그 물고기는 실제로 위험하기 때문이다. 어항 사진 분석 결과가 있으면 CFD 315케이스로 학습한 ROM(PCA 6성분 + Ridge)으로 바닥층 산소 분포 지도를 그린다.

(2) 폭기 입력을 정격전력으로 교체

약/보통/강 3단계 드롭다운을 기포기 정격전력(W) 연속 입력으로 바꿨다. 기계팀에서 받은 환산식을 그대로 구현했다.

Q_air = 0.480 · P [L/min]
0.3009·x^1.511 + 0.0578·x = 0.3587·(P/2.5)  (x = α_g/α_g0)
K_La(P) = 2.160·x + 0.444 [1/h]

좌변이 x에 대해 순증가라 해가 유일하므로 이분법으로 정확히 푼다. 문서의 실용 근사 (P/2.5)^0.70은 1~5 W에서만 오차 1% 이내이므로 초기 구간 설정에만 썼다.

(3) 다종 사육

어항 하나에 여러 종을 등록하고 종마다 애칭·마릿수를 갖게 했다. 산소 부하는 종별로 계산해 합산하고, 적정 수온은 모든 종의 교집합, 위험 임계는 최댓값(가장 까다로운 종)을 쓴다.

(4) 상태를 보여주는 방식 개선

  • 홈 어항 위젯 — 등록한 어종이 실제로 헤엄친다. 양호는 활발한 왕복, 주의는 느려지고 기울어짐, 위험은 수면 근처에서 헐떡임(산소 부족 물고기의 실제 행동). 물빛·기포량도 함께 바뀐다. 색 하나만 바꾸면 화면을 스쳐 볼 때 놓치기 때문에 색·속도·자세를 동시에 바꿨다.
  • 안드로이드 홈 화면 위젯 — 앱을 열지 않고 수온·탁도·용존산소와 상태를 확인한다.
  • 팝업 알림 — 위험·주의 두 등급만 팝업으로 띄운다. 정상 복구는 목록에만 남긴다.

(5) 백그라운드 감시 및 설정 저장

  • 포그라운드 서비스 — 앱을 닫아도 BLE 연결과 경고 판정을 유지한다.
  • 설정 영속화 — 어항 치수·기포기·수위·어종 목록·급여 시간·사진 분석 결과를 폰에 저장해 재실행 시 온보딩을 건너뛴다.

3.3 검증 현황

항목내용
CFD 검증 범위 Stage B 산소 방정식을 A층 CFD 315케이스 전량에 풀었다. 보존형 유한체적, 질량보존 오차 1e-10, 139.6분 / 6워커. 학습 데이터의 장애물 수 분포는 0/1/2개 = 1/60/254이므로 유효범위는 2개 이하.
축약 오차 결핍 기준 3.8%, 용존산소 기준 0.11%(0.0091 mg/L, 위험까지 여유의 0.45%). 단 축약이 결핍을 과소평가하는 방향이므로 안전측이 아니다. 보수적으로 쓰려면 1.04를 곱해야 하는데 현재는 미적용이며, 표시값은 실측 그대로다.
환산식 검산 P = 2.5 W에서 x = 1이 정확히 해가 되어 K_La = 2.604로 문서값과 일치. P = 4.17 W에서 K_La = 3.53으로 기존 정본 3.618과 2.4% 차이(격자 편향 이내). P = 0에서 자유수면 항 0.444만 남는다.

3.4 남은 과제

구분항목내용
미검증 상수 U1 · 탁도→산소요구량 계수 0.4 mg/h per NTU. 근거 문서가 없는 임시값으로, 25 NTU에서 10 mg/h가 되도록 역설정했다.
U2·U3 · 어종별 체중·소비율 문헌 추정값. 출처 부여와 실측 교정이 필요하다.
U4 · 대사율 온도의존 계수 2.0. 어류 문헌값 2~3 중에서 골랐으나 출처를 아직 붙이지 못했다.
전력→공기량 변환계수 0.480 L/(min·W). 1점 앵커를 지나는 직선이라 「기울기 가정 + 절편 0 가정」이 들어간다. 이 모델의 유일한 미검증 고리다. 실측 기포기 몇 대의 (W, L/min) 데이터를 받으면 계수 하나만 교체하면 된다.
기능 ROM 식물 기저 u_plant를 받으면 [S2] 임시 조치를 정식 처리로 바꿀 수 있다.
물리 모델 회귀 테스트 물리 모델이 이 과제의 핵심 기여인데 자동 검증이 없다. 앵커 몇 개를 박아 상수 변경 시 즉시 잡히게 해야 한다.
탁도 프로브 실장 현재 시연 모드로 대체 중. 실측 전환 후 영점 보정과 K 계수 교정이 필요하다.
보안·배포 API 키 노출 Gemini API 키가 APK에 평문으로 들어 있다. APK는 누구나 압축을 풀어 볼 수 있다. 최소한 패키지명·서명 기반 앱 제한을 걸고, 실배포 시에는 서버로 옮겨야 한다.
ROM 계수 파일 용량 약 8 MB로 APK 대부분을 차지하고 앱 시작마다 파싱된다. 저사양 기기에서 초기 로딩 시간을 측정해야 한다.

3.5 자체 평가

이번 3주 동안 반복된 실패 방식은 하나로 모인다 — 「에러 없이 조용히 잘못된 값을 보여주는 것」이다. BLE 권한이 없으면 빈 목록이 오고, 알림 권한이 없으면 알림이 그냥 안 뜨고, 센서가 빠지면 마지막 값이 「정상」으로 얼어붙고, CDN 실패는 200번대 응답으로 위장하고, 안드로이드 14 서비스 권한 누락은 빌드를 통과한다. 어항 관리 앱에서 이 실패 방식은 특히 위험하다. 사용자는 「알림이 안 왔으니 괜찮은 것」으로 읽기 때문이다.

그래서 후반 작업에서는 판정 로직보다 「모를 때 모른다고 말하게 만드는 일」에 더 많은 시간을 썼다. 센서 무효값을 「--」로 표시하고, 위젯에 갱신 시각을 함께 찍고, ROM 형상이 검증되지 않은 운전점에서는 지도를 그리지 않고 사유를 밝히고, 시연용 가상값에는 「밝히지 않으면 결과 조작」이라고 코드에 못 박은 것이 모두 같은 판단에서 나왔다. 미검증 상수를 U·C·N·S 태그로 분류해 코드에 남긴 것도 같은 이유다.
